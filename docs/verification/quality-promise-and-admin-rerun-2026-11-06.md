# `--quality` on labeled requirements, and admin re-run after FIX R4

Two measurements that needed a model:
1. How well does `--quality` classify requirements written by people,
   against labels made independently of codetospec (IMPROVEMENTS #14)?
2. Does re-running admin after the role-sentence change (FIX R4) reword
   its role rules and nothing else?

## Revisions and commands

- codetospec `74f7781` (branch `checker-catalog`); model
  `gemini-3.8-flash` through Gemini's OpenAI-compatible endpoint.
- Quality:
  `CODETOSPEC_EVAL=1 go test ./internal/quality -run EvalPromise -v`
  with `LLM_BASE_URL`, `LLM_MODEL` and `LLM_API_KEY` set, and
  `CODETOSPEC_EVAL_RECORD` kept.
  - The set is Dalpiaz et al.'s relabeled PROMISE NFR set
    (explainable-re/RE-2019-Materials, `promise-reclass.csv`, GPL-3.0),
    downloaded at run time and never committed.
  - Each requirement goes through the production prompt as a rule's
    requirement, with no title.
- Admin: a scratch copy of `~/spec-graphs/admin` (that output untouched),
  re-run with `scanwebapp.sh admin` and the remap's flags (`--quality
  --crosscheck --acceptance --write-domain-model`), webapp
  `c55b04b0090`, inheriting from `~/spec-graphs/pkg`. Then `codetospec
  diff` against the original, and `export --format cerbos` with the
  review's checkers file, `cerbos compile` on it.

## Quality on PROMISE

625 requirements, none left unanswered (no failed batch), 106 seconds.

| measure | result |
|---|---|
| attribute accuracy (answer among the class's attributes) | 521/625, 83.4 % |
| quality detection (an attribute vs the separate `IsQuality` label): precision | 368/400, 92.0 % |
| quality detection: recall | 368/382, 96.3 % |

How each PROMISE class maps (the mapping the scoring test pins):
- PROMISE classes map to `internal/quality`'s attributes: A
  availability, FT reliability, L compliance, LF and US usability, MN
  maintainability, PE performance_efficiency, PO portability, SC
  scalability, SE security.
- F expects no attribute.
- O (operational) was decided first. ISO 25010 has no operational
  characteristic, and PROMISE's O requirements state the operating
  environment, so portability or compatibility counts as right.

| class | correct |
|---|---|
| F | 216/255 |
| US | 61/67 |
| O | 50/62 |
| SE | 58/66 |
| PE | 46/54 |
| LF | 29/38 |
| A | 19/21 |
| SC | 11/21 |
| MN | 12/17 |
| L | 10/13 |
| FT | 8/10 |
| PO | 1/1 |

- **Weakest:** scalability, maintainability and look-and-feel. The
  record keeps per-class counts, not the confusions, so which attribute
  each missed requirement got isn't known.
- **F partly disagrees by design.** Dalpiaz labels some F requirements
  as also carrying a quality aspect. An attribute on one of those counts
  as correct detection but a wrong attribute.
- **One run, one model.** No repeat was made to measure flips.

## Admin after FIX R4

- `diff`: 46 role rules `reworded` with their ids kept, as the plan
  expected. 1 rule removed: the `testutil` role rule FIX R1's exclusion
  drops. 7 capability rules changed `verdict`. 1,134 unchanged.
- **The 7 verdicts.** Each of the 7 gained its first test (FIX R3:
  package-level variables count as test targets). The crosscheck folds
  the nearest tests into its key, so each was judged again with the test
  beside its code: 6 went from supported to partial, 1 from partial to
  supported.
- **Tokens:** map 24,263 + 345 (the chunks whose role rules changed),
  crosscheck 79,234 + 1,406, quality 4,575 + 729, acceptance
  112,541 + 4,498; no reduce.
- **Export:** 37 operations and 30 deny rules before and after, 96/96
  `cerbos compile`.

## Limits

- The quality score measures the classifier on prose written as
  requirements, not on the rules the map writes from code.
- The nature check of IMPROVEMENTS #14 (technical, business or open, on
  the sets labeled both functional and quality) isn't built.
- The admin re-run is a scratch copy. `~/spec-graphs/admin` is
  regenerated by the remap (`scripts/remap.sh`), still owed.
