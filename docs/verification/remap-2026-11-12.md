# Remap of 2026-11-12: a false start, and a correction

This remap was meant to bring every output under `~/spec-graphs` up to the
checkouts' new commits. It found instead that the outputs were already
current, and that three earlier records name the wrong districts-jobs
commit.

## The false start

- `VARIANCE=0 scripts/remap.sh` started at 14:10 with webapp at
  `01343340ac2`. That's a feature branch
  (`os/IDENT-282/ingest-user-attributes-at-users-service`), checked out at
  10:33 for unrelated work, not master.
- pkg and admin came from the caches. ai-guide, assignments and coaches
  were remapped from the feature branch, and so was districts' map phase.
- webapp moved back to master (`c55b04b0090`) at 15:38, during districts'
  reduce. The run was stopped at 15:40. The end-of-run check would have
  refused it, but only after the remaining services had run.
- All eight webapp outputs were restored from the snapshot
  (`~/spec-graphs.before-remap-2026-11-12`, taken by the script), and each
  is identical to it. The calls already made stay in the caches.

## The districts-jobs run

- The checkouts were kept at webapp `c55b04b0090e6d0f2df471bef5f37a8a78b58883`
  and districts-jobs `93d6ee686`, codetospec `bb96d0c` (after #29).

## Results

- No map or reduce entry was stale in any of the 22 modules. Every output
  is byte-identical to the snapshot, `.codetospec/` included.
- `drift` against `93d6ee686`: 0 stale, 0 broken, 0 moved, 0 affected in
  every module.
- The corpus passes with no baseline change. It has no districts-jobs

## Correction: the districts-jobs commit

The remap of 2026-11-11 mapped districts-jobs `93d6ee686`, not `dde732546`.

- That checkout was pulled to `93d6ee686` at 19:25 on 2026-11-11.
- The remap's log was created at 19:26, a minute later (the record's
  "19:23" is early), and its preflight prints
  `districts-jobs 93d6ee6866af3eaa3433214d438377ad56338e14`.
- Its districts-jobs step started at 19:36. The admin-reports map
  entries citing the changed files were written at 20:01.

The commit was copied wrongly into three records:

| record                          | says        | should say                                          |
| ------------------------------- | ----------- | --------------------------------------------------- |
| `remap-2026-11-11.md`           | `dde732546` | `93d6ee686`, 20 commits after `bc74efd4ad3`, not 15 |
| `datastore-kinds-2026-11-12.md` | `dde732546` | `93d6ee686`                                         |
| `sql-table-usage-2026-11-12.md` | `dde732546` | `93d6ee686`                                         |

Their measurements stand: each was taken on the outputs mapped from
`93d6ee686`.

## Limits

- `remap.sh` compares the checkouts only once, after every output has
  run. A checkout that moves early costs the whole run before the check
  refuses it.
- The check can't see a checkout that was already on the wrong branch
  when the run started. It records whatever commit it finds.
